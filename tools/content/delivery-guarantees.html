The trade-off

A sender can't always tell whether a message arrived. If the reply is lost, the message might have been written or might not. The sender then has to pick a policy:

  • At most once: don't retry. Simple and cheap, but anything that failed is lost.
  • At least once: retry until acknowledged. Nothing is lost, but if only the acknowledgement was lost, the event arrives twice.
  • Exactly once: retry, and also make repeats harmless. This is correct, but needs more machinery: idempotent writes, deduplication keys, or transactions.

In practice, "exactly once" means at-least-once delivery combined with idempotent processing, not a message that physically travels once. Apache Kafka, for example, builds it from idempotent producers (a repeated send is recognised and dropped) and transactions (writes and consumed offsets commit together). That is cheap for the first piece and costs more coordination for the second, and it covers only what happens inside Kafka. Effects on outside systems still need their own idempotence.

How to use it

  1. Decide what's worse: a gap or a repeat. For a click counter either is a small error. For a payment, both are serious.
  2. Default to at-least-once with idempotent consumers. Give each event a unique ID and make the receiving write safe to repeat (an upsert by key, for example).
  3. Use transactions where duplicates are expensive, and accept the extra latency and throughput cost.
  4. Make side effects idempotent too. Emails, charges and calls to other services need keys or an outbox pattern, because the pipeline's guarantee ends at its edge.

Example

A pipeline loads order events into a warehouse. With at-most-once, a network blip silently drops a few orders and revenue reports run low. With plain at-least-once, a retry double-counts some. The team keeps at-least-once, adds the order ID as a key, and merges on it. The warehouse now has each order exactly once, and the pipeline itself stays simple.

Watch out for

  • The costs here are illustrative. The extra work for exactly-once in the animation is a made-up number. Real overhead depends on the system and the settings, so measure it.
  • Exactly-once has a boundary. It holds inside one system. Across systems, you need idempotent receivers or you are back to at-least-once.
  • Ordering is a separate question. Retries can also deliver messages out of order.
  • Related: retries are what make at-least-once work, and they can overload a struggling service (retries vs. load). Faster pipelines make all of this harder (batch vs. streaming), and the underlying uncertainty is the one in the CAP theorem.
