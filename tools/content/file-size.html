The trade-off

In a data lake or lakehouse a table is stored as many files, and every query has to open the files it needs. Opening a file has a fixed cost: listing it, fetching its metadata, scheduling a task, reading the footer. With very small files, that cost is paid over and over, and it can be bigger than the cost of reading the data. This is the small files problem, common after streaming ingestion or over-fine partitioning.

Very large files go wrong the other way. A query can skip a file only as a whole, so when it wants a few rows from many places it still has to read every file that contains one of them. The larger the file, the more it reads that it doesn't need. Between the two the cost curve is U-shaped, and its lowest point moves with the workload. Selective lookups favour smaller files, while large scans favour larger ones. Platforms reflect this: for example, Microsoft Fabric's documentation describes a target of about 128 MB for small tables, growing to about 1 GB for very large ones.

How to use it

  1. Look at the queries. Mostly dashboards over large ranges can use big files. Many point lookups and narrow filters want smaller ones plus clustering or sorting on the filtered column.
  2. Compact regularly. Streaming and frequent small writes produce many small files, and periodic compaction (or auto-compaction) merges them.
  3. Partition coarsely. Partitioning by a high-cardinality column multiplies the number of small files. Partition by something like date and cluster on the rest.
  4. Check the file count and average size in table metadata. A table with millions of files of a few megabytes is the usual warning sign.

Example

A streaming job writes a new file every few seconds, and after a month a table has 3 million files averaging 2 MB. A report that scans one week takes minutes, most of it spent listing and opening files. A nightly job compacts each day into files of about 256 MB. The same report drops to seconds, and storage listing costs fall as well.

Watch out for

  • The costs here are a model. Real per-file overhead, throughput and skipping depend on the engine, the format and the storage layer. Rules of thumb like "128 MB to 1 GB" are starting points to benchmark, not constants.
  • Compaction isn't free. It rewrites data, and raising the target size later rewrites files that were already compacted.
  • Large files make small updates expensive. Changing one row can mean rewriting a whole file, which matters for tables with frequent merges.
