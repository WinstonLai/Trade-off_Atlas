The trade-off

Without an index, a query has to read the whole table to find what it wants. An index is a second, sorted copy of some columns that lets the database find matching rows directly. It converts a scan into a lookup. The cost is that every insert, update and delete must also update every index, and each index takes storage and memory.

The benefit has diminishing returns, because workloads are skewed: a handful of query shapes account for most of the traffic. The first few indexes cover those, while later ones serve rare queries. Write cost, by contrast, grows with each index you add. The research literature states the general version as the RUM conjecture: you can't minimise read overhead, update overhead and memory all at once. Improve two and the third gets worse.

How to use it

  1. Start from the queries, not the columns. Find the slow and frequent ones in query logs and index for those.
  2. Know the read/write ratio. A reporting replica can afford many indexes. A table receiving a firehose of inserts can afford very few.
  3. Prefer one composite index that serves several queries over many single-column ones, and drop indexes that no query plan uses.
  4. Re-check after changes. Index usage statistics show which ones earn their keep.

Example

An events table starts with indexes on six columns "just in case". Reads are quick, but ingest can't keep up and storage doubles. Query logs show two indexes serve 95% of lookups and three are never used. Dropping those three makes ingest faster by about a third and barely changes read times.

Watch out for

  • Unused indexes still cost. They slow writes and use memory even if no query touches them.
  • The cost curve here is a model. Real index maintenance depends on the engine: B-trees, LSM trees and column stores pay in different places.
  • Related: an index is another stored answer to avoid recomputation, like a cache (time vs. space), and a copy that must be kept in step, like denormalized data.
