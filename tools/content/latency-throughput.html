The trade-off

Latency is how long one request takes. Throughput is how many requests complete per second. They sound like the same thing, but optimising one often costs the other. Anything with a fixed cost per call (a network round trip, a disk flush, a GPU kernel launch, a transaction commit) goes faster overall when you do more work per call.

The catch is that each item in a batch waits for the rest. Throughput climbs quickly at first, then flattens as the overhead becomes a small share of the total, while latency keeps rising in a straight line. Little's law ties them together: the number of items in flight equals throughput × latency, so to hold latency down while raising throughput you need to add capacity, not just batch.

How to use it

  1. Start from a latency budget (for example, 95% of requests under 200 ms), then find the largest batch or concurrency that meets it.
  2. Measure the fixed overhead. If it's tiny, batching gains little. If it dominates, batching is the main lever.
  3. Use a time cap as well as a size cap. "Send when 100 items are ready or after 10 ms" bounds the wait when traffic is light.
  4. Judge by percentiles, not averages. A batch hurts the slowest items most.

Example

A service writes each event to a database with its own round trip, and tops out at a few hundred writes per second. Buffering events for 20 ms and inserting them together raises capacity ten-fold, and the 20 ms is invisible to users. The same trick on a checkout page would add visible delay to every click, so there it makes sense to keep calls small and add servers instead.

Watch out for

  • Queues hide the latency. A system pushed past its throughput limit doesn't slow down smoothly, its queues grow until latency explodes. See utilization vs. flow.
  • One failure can fail the batch. Decide in advance how partial failures are retried.
