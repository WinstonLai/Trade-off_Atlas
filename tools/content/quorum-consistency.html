The trade-off

The CAP theorem covers what happens during a network split. PACELC adds the more common case: else, when there is no partition, you still trade latency against consistency. Replicas take time to agree, and the more of them you wait for, the longer you wait.

Many replicated stores let you tune this with quorums. With N copies, a write waits for W acknowledgements and a read asks R replicas. If R + W > N, every read set overlaps every write set, so a read always meets at least one replica with the latest value. Otherwise it can return stale data, but faster. Each operation's latency is set by the slowest replica you have to wait for.

How to use it

  1. Decide what stale means for this data. A like count can be seconds old. An account balance or inventory count usually can't.
  2. Pick the shape of the quorum from the workload. Read-heavy data: small R, large W. Write-heavy: the reverse. Balanced: majorities on both.
  3. Set it per operation where your database allows, so critical reads can ask for more replicas than casual ones.
  4. Measure tail latency. The slowest replica, not the average one, determines how a large quorum feels.

Example

A shopping site keeps three copies of each record. Browsing the catalogue reads from one replica (R = 1): it's fast, and a price a few seconds out of date does no harm. At checkout, the stock check and order write both use majorities (2 + 2 > 3), so two customers can't both buy the last item, at the price of a slightly slower final step.

Watch out for

  • R + W > N is necessary, not complete. Concurrent writes, clock skew and failed partial writes can still produce surprises, and quorums alone don't give you transactions.
  • Higher quorums reduce availability. If W = N, a single down replica blocks every write.
  • The strict end of this dial is the world of normalized, single-source-of-truth data. The loose end is eventual consistency and caches: time vs. space has the same freshness cost.
