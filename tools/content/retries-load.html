The trade-off

Most failures between services are brief: a dropped connection, a restarted instance, a slow reply. Retrying the call makes these invisible, which is why almost every client library does it. But every retry is extra traffic. If each failed call is retried three times, a backend that is failing most requests sees several times its normal load.

That is the dangerous part. Overload makes calls fail, failures cause retries, retries add load, and more calls fail, a positive feedback loop. Google's SRE book describes this as one of the ways cascading failures start. So the same setting is good for blips and harmful during a real problem, and the more it helps in good times, the more it can hurt in bad ones. The fix is not "no retries" but limited ones: a cap on attempts per request, backoff with random jitter so clients don't retry in sync, and a retry budget that allows retries only while they are a small fraction (the SRE book uses 10% as an example) of total traffic.

How to use it

  1. Retry only what's safe. Calls that can be repeated without harm (reads, idempotent writes) can be retried. Others need an idempotency key first.
  2. Cap and spread them. A few attempts at most, with exponential backoff and jitter.
  3. Add a budget. Limit retries as a share of traffic per client, so a widespread failure produces a small, bounded extra load.
  4. Fail fast when the backend is clearly down. Circuit breakers and load shedding stop clients from queueing work that can't succeed.
  5. Retry at one layer. If three layers each retry three times, one failure becomes twenty-seven calls.

Example

A service runs at 80% of capacity. A database hiccup makes 30% of calls fail, and every client is set to retry three times. Within seconds the service is receiving nearly three times its capacity, requests start timing out, and the timeouts are retried too. The hiccup lasts a minute; the outage lasts half an hour. After the incident the team adds jittered backoff and a retry budget, and the next hiccup passes unnoticed.

Watch out for

  • The curves here come from a toy model. The way throughput collapses under overload differs by system, and real failures are rarely this uniform.
  • Retries stack up the call chain. A retry in the web tier, the API tier and the database client multiply together.
  • A retry can hide a real fault. Watch the retry rate as a metric. A rising one is an early warning.
  • Related: this is the same cliff as in utilization vs. flow, where waiting time explodes near full load. It also interacts with latency vs. throughput, and it is why networked services need to think about failure as normal.
