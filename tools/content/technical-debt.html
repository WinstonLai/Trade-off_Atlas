The trade-off

Skipping tests, copy-pasting code or hard-coding a value gets a feature out sooner. That's the principal you borrowed. Afterwards, every change that touches that code takes longer, breaks more easily and needs more explaining. That's the interest.

Debt isn't automatically bad. Like a financial loan, it's worth taking when the payoff comes before the interest piles up: a prototype, a market window, a demo. It becomes a problem when it's unintentional or never repaid.

How to use it

  1. Ask about the horizon. Will this code live for two weeks or two years? The longer it lives, the costlier the shortcut.
  2. Make debt deliberate. If you take a shortcut, write it down: what was skipped, why, and when it will be fixed.
  3. Pay interest continuously. Reserve a steady share of each iteration (often 10–20%) for refactoring and clean-up.
  4. Pay down where it hurts. Prioritize debt in code that changes often. Messy code nobody touches costs little.

Example

A startup hard-codes pricing rules to launch before a conference, which is a sensible loan. Six months later, every pricing change takes a week and causes bugs. The team spends two sprints extracting pricing into configuration, and changes drop to an afternoon.

Watch out for

  • "We'll fix it later" rarely happens unless the time is actually set aside.
  • Debt is invisible to non-engineers. Translate it into delivery speed ("features now take 2× longer") to get time to repay it.
  • The opposite trap is over-engineering for a future that never comes. See flexibility vs. simplicity.
