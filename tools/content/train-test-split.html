The trade-off

To know how well a model works on new data you have to try it on rows it hasn't seen. But the same rows can't also train it. A split divides a fixed pool of labelled data between two jobs that both want more of it:

  • More training data lowers the model's error, with diminishing returns (the learning curve).
  • More test data makes the score more precise. The margin of error shrinks roughly with the square root of the number of test rows.

A small test set gives a noisy score: a model that looks good might just have been lucky on 100 rows. A small training set gives a weaker model. The total uncertainty is lowest somewhere in the middle, but the curve is flat across a wide range, so the exact percentage matters less than avoiding the extremes. With very little data no split works well, and with a lot of data almost any sensible one does.

How to use it

  1. Start with a conventional split (roughly 70/30 to 90/10, depending on size). It is rarely badly wrong.
  2. Count test rows, not percentages. What matters for precision is how many examples there are, and especially how many of the rare class, in the test set.
  3. With little data, cross-validate. Every row is used for testing exactly once and for training the rest of the time, and you average the scores.
  4. Keep a separate final test set if you also tune the model on the validation score, and look at it once.
  5. Retrain on everything at the end. After evaluation, the model you ship can use the test rows too.

Example

A team has 2,000 labelled support tickets. A 95/5 split gives 100 test tickets, and the accuracy score swings by several points between random splits, so they can't tell whether a new model is really better. At 80/20 the score is steady enough to compare models. They later run 5-fold cross-validation for the final comparison and retrain the winner on all 2,000.

Watch out for

  • The curves here are a model. The learning curve shape and the "defensible error" combination are simplified. Real learning curves depend on the model, and the right split depends on your goals.
  • Leakage ruins everything. Duplicates, the same customer in both sets or time-ordered data split at random make the score look better than reality. Split by customer or by date where that matches how the model will be used.
  • Reusing the test set wears it out. Every time you choose a model by its test score, the score becomes a little optimistic.
