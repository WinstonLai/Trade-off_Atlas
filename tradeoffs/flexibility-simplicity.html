Flexibility vs. simplicity

Every abstraction is a bet on the future. It makes the change you predicted cheaper and everything else a little harder to understand.

Flexibilityvs.Simplicity

The trade-off

Interfaces, plugin systems and configuration layers let code adapt without rewrites. But each layer is something every future reader has to understand, and something every unpredicted change has to work around.

Whether a layer pays off depends on how likely the predicted change really is. "You aren't gonna need it" (YAGNI) is a reminder that most predicted changes never happen, and the ones that do often arrive in a shape nobody expected.

How to use it

  1. Name the change the abstraction is for. "So we can swap payment providers." If you can't name one, you probably don't need the layer.
  2. Estimate its likelihood and timing. Is there a real second use case today, or a hypothetical one in some future year?
  3. Wait for the second, or even third, example. Duplicate once, then abstract when the pattern is real (the "rule of three").
  4. Prefer abstractions that are easy to remove over ones that are hard to add later, and the other way round for public APIs.

Example

A team wraps their only database in a generic repository layer "in case we switch to NoSQL". Three years later they never switched, but every new query has to be squeezed through the generic interface, and the database's best features are unusable. Meanwhile, a second payments provider was added in a week because that integration was abstracted only once a second provider was actually signed.

Watch out for

  • Some boundaries are worth it early: public APIs, data formats and security boundaries are expensive to change later.
  • Simplicity isn't the same as no structure. Clear naming and small functions cost almost nothing and help every change.
  • Under-designing has its own costs. See technical debt.
