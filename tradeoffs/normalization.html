Normalization vs. denormalization

Store each fact once and keep it consistent, or copy it next to where it's read and make queries fast. You're trading write integrity against read speed.

Write integrityvs.Read speed

The trade-off

A normalized schema stores each fact exactly once: a customer's name lives only in the customers table. Updates are simple and can't contradict each other, but reading anything useful means joining tables together.

A denormalized schema copies facts to where they're needed: each order row carries the customer name. Reads are fast and simple, but every copy must be kept in sync. Storage grows, and a missed update leaves the data contradicting itself.

How to use it

  1. Check the read/write mix. Transactional systems (many small writes) lean normalized. Analytics and dashboards (many large reads) lean denormalized.
  2. Ask how often the copied fact changes. Copying something that rarely changes (a country name, the price at time of order) is cheap and safe.
  3. Keep one source of truth. Normalize the system of record, then build denormalized tables or views from it for reading.
  4. Automate the copies. If you denormalize, update copies from a pipeline or trigger, not by hand.

Example

An online shop keeps its order database normalized so that addresses and prices stay correct. Every night, a pipeline builds a wide "orders_enriched" table for the analytics team, so dashboards scan one table with no joins and stay fast even over years of data.

Watch out for

  • Some copies are actually correct. The price at the time of the order should be copied, because it must not change when the catalogue does.
  • Modern columnar warehouses make wide tables cheap, which shifts the balance for analytics.
  • Copies spread across systems bring the same consistency question as CAP.
