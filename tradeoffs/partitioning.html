Hash vs. range partitioning

Splitting data across machines by key range keeps related rows together, which makes range queries cheap but concentrates bursts of new keys on one machine. Splitting by hash spreads the load but scatters neighbours.

Even loadvs.Range queries

The trade-off

To scale beyond one machine you partition (shard) the data by key. Range partitioning assigns each partition a contiguous slice of the key space, so rows with nearby keys live together. Querying "all events between 9:00 and 10:00" touches one or two partitions. Hash partitioning assigns rows by a hash of the key, which scatters them uniformly across partitions.

Each choice has a weak spot. Real keys are rarely uniform: timestamps, auto-incrementing IDs and popular names all cluster. With ranges, a burst of recent keys all land on the newest partition, which becomes a hot spot that caps the whole cluster's throughput however many machines you add. With hashing the load is even, but a range query has to fan out to every partition and merge the results.

How to use it

  1. List the access patterns. Point lookups by key? Hash is natural. Frequent range scans or time-window queries? Range keeps them local.
  2. Look at the write pattern. Monotonic keys (time, sequence numbers) under range partitioning funnel all writes to one end.
  3. Combine them. A composite key such as (hash of user, timestamp) spreads users across partitions while keeping each user's history contiguous and range-scannable.
  4. Plan for change. Use many more partitions than machines, or consistent hashing, so adding a machine moves only a fraction of the data.

Example

A sensor platform partitions readings by timestamp range so dashboards for "the last day" read a few partitions. At peak, every device writes to the current-hour partition and one node saturates while the rest sit idle. Re-keying by (device ID hash, timestamp) spreads the writes evenly and still lets each device's recent history be read from one place.

Watch out for

  • Hash doesn't fix a hot key. One very popular record still lands on one partition. Replicating or splitting that key is a separate remedy.
  • The model is simplified. Here the hot traffic fits inside the last range. Real systems also rebalance ranges automatically.
  • Related: spreading data over machines is where the CAP theorem begins to matter, and fan-out queries are a cost of the same kind as joins over normalized data.
