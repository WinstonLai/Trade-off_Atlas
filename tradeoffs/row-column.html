Row vs. column storage

Storing each record together makes fetching or changing one record fast. Storing each column together makes scanning a few columns across millions of records fast. The layout decides which job is cheap.

Row store (OLTP)vs.Column store (OLAP)

The trade-off

A row store (most traditional databases) writes all the values of a record next to each other on disk. Reading or updating one customer is a single read. A column store writes each column's values together instead. A query that needs two columns out of fifty reads two columns' worth of data and skips the rest.

Columns also compress very well, because values in one column look alike, and they allow vectorised processing. The price is on the other side: assembling a whole record means gathering one value from each column, and a single-row insert or update touches every column's storage. This is why transactional systems (OLTP) usually use rows and analytical warehouses (OLAP) usually use columns.

How to use it

  1. Look at the access pattern. Mostly "get or change one record by key"? Rows. Mostly "aggregate a few columns over many records"? Columns.
  2. Count the columns you actually read. The wider the table and the narrower the query, the bigger the column store's advantage.
  3. Separate the workloads. A common design keeps the transactional database in rows and copies data to a columnar warehouse for reporting.
  4. For mixed needs, consider hybrid formats (row groups with columnar chunks, such as Parquet) or engines that keep both layouts.

Example

An orders table has 40 columns and 500 million rows. "Total revenue by day" needs two of them. A row store reads all 40 columns of every row, while a column store reads two and compresses them well, so the report drops from minutes to seconds. The checkout service that loads one order by ID is better off on the row store, where that whole record sits together.

Watch out for

  • Frequent small writes are slow and costly in column stores, which prefer large batched loads.
  • Wide scans of all columns remove the benefit, as shown above. If every query wants nearly every column, layout matters little.
  • The numbers here are a simple model (a fixed cost per place read plus a cost per value). Real engines add compression, caching and indexes. Related: normalization decides how many tables there are, while this decides how each table is laid out on disk.
