Time vs. space (caching)

Spend memory to remember answers and you save the time of computing them again. But each extra byte of cache helps less than the last.

Memoryvs.Compute time

The trade-off

Many programs can trade space for time: store a result (a cache, an index, a precomputed table) so you don't redo work. A hit is fast; a miss pays the full cost, plus the cost of filling the cache.

Because some items are requested far more often than others, the first slice of cache captures most of the benefit. Doubling the cache from there adds less each time, while memory cost, and the work of keeping the cache fresh, keeps growing linearly.

How to use it

  1. Measure the access pattern. Caching helps when a small set of items gets most of the requests, and does little for uniformly random access.
  2. Size the cache at the knee of the hit-rate curve, not at "as big as possible".
  3. Decide how stale is acceptable. Every cache is a copy; set an expiry or an invalidation rule on purpose.
  4. Price the miss. Caching is worth more when the miss is slow or expensive.

Example

A product page query takes 200 ms. Caching the 5% most-viewed products serves 70% of requests in 2 ms and cuts average latency by two thirds. Caching the next 20% of the catalogue costs four times the memory for about 13 points more hit rate.

Watch out for

  • Stale data. "There are only two hard things in computer science: cache invalidation and naming things."
  • Cold starts. After a deploy or restart the cache is empty and the slow path takes the full load.
  • Compare exact vs. approximate and normalization, which trade effort and storage for speed in the same way.
